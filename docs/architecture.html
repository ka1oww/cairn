Cairn — the dependency map

Every piece of the app as a node; an arrow means “knows about” and always points downward. Point at any node and its inward arrows are what breaks if it changes. Drawn 22 Aug 2026 from main (PRs #7–#10 merged) and design round 7 (PR #11); updated the same day for the app scaffold, 24 Aug 2026 for the paste-and-confirm flow — the first real screens — Today, the day page that replaced its placeholder as the launch surface, and the Trail with the tab container; and 25 Aug 2026 for the Pool, the third tab. The greppable twin of this page is architecture.md.

The app has a way in, and a trip with all three of its destinations in it. The paste-and-confirm slice replaced the scaffold's proving screen and its disposable trip_drafts table: paste a plan, see what was understood with the doubt surfaced per cause, flip ambiguous dates in one tap, accept — and the itinerary persists into Drift, local-only for now. Today then replaced that slice's placeholder: the app opens on the day page for today's date — the day's identity, its stops in pasted order, a time only where the plan starred one. The Trail added the trip-level view — one node per day on the winding path, a flag on today — and the real container it and Today live in: a tab bar built so the Pool becomes a third entry, and shown without one until it existed. The Pool is now that third entry: the trip's photos grouped by day, newest first, over a read-only seam with an empty in-memory pool behind it — capture and every write path land separately, so what a phone sees today is the empty state. There is one day screen and no separate day detail; the Trail opens that same widget for every node it draws. lib/README.md spells these bands as directories. Every other designed screen, the three services, the platform glue and the whole remote side are still intention, drawn here so the intention is inspectable.

Why the seam is the map’s centre

Every question a screen asks funnels down through app state into one layer, and that layer alone knows both storage backends exist. A provider asks “photos for day 4” and cannot tell — by construction — whether the answer came off disk or over the wire.

Skip it and every screen grows its own opinion about caching, retries and which copy of a photo is real: eight opinions, all subtly different, none testable in isolation. The seam is where the outbox ordering, the day_pages conflict fallback, deletion refetch and the translation of package dialects into the vocabulary live — so they live nowhere else.

Invariants the import graph won’t show

  1. “A day’s clock is fixed where it starts” is encoded three times — in cairn_model, trip_moments and photo_day_assignment — by siblings that cannot see each other. Change one, change all.
  2. The gate rule exists twice on purpose: GateState on the phone, day_page_is_open in SQL for signing downloads. They must move together.
  3. The trip clock has one source — the trips row. No phone ever infers it; two phones inferring differently is silent schedule drift.
  4. The ping derivation is frozen. Any change splits devices mid-trip; the only safe change is a loud namespace bump (v2 → v3).
  5. Multiplication and addition, never bit-shifts — dart2js ints are 32-bit under shifts. Golden tests pin it.
  6. RLS refuses by filtering, not raising. Assert on table state afterwards, never on whether a statement threw.
  7. Membership checks only via is_trip_member/is_trip_starter; never force row level security — either revives infinite recursion.

Honesty about the gaps

Drawn as open, not settled. None is a contradiction: in each case the decision record is clear and the code is behind it, acknowledged and queued in docs/roadmap.md.

  • Starter & container decisions settled, unimplemented. Rename and invites flat; delete gated once others’ photos exist; removal power passes to the longest-standing member. Today’s schema is starter-only rename/delete with no succession, and Trip.canRemove knows nothing of it. Queued near-term.
  • No download path. Only uploads exist. The requirements are written down — which is exactly why the blank is the most dangerous one on the map.
  • Sync & conflict policy undecided beyond three written notes; nothing reconciles rows against R2 objects in either direction.
  • Riverpod and Drift are validated, not decided — the demo makes the argument; no decision file records the choice.
  • One fixed clock per trip on the server (v1). First/last-day windows and the country-change rule live only on the phone; grill round one §2 makes the itinerary a synced shared fact, but nothing implements that yet.
  • The book’s interior is designed — round 9 drew it against the captain’s printed reference; the printed page is not designed, and the book is deliberately after the first release.
  • In-transit photos on a multi-zone day are parked — refusal (outsideTrip) plus manual placement is the current answer.
  • Thumbnails, keepalive, CI: no thumbnail pipeline; the between-trips dormancy keepalive is planned only; no CI runs any test on any PR.
  • Nothing has touched a hosted Supabase project or a real R2 bucket. supabase db push against a throwaway project is still the gate.
